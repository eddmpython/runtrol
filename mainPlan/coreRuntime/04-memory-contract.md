# 메모리 계약 . 숫자로 고정한다

운영자 지시 "아주 메모리 효율적이여야한다" 를 형용사가 아니라 **게이트가 실측하는 계약**으로 바꾼다.

## 실측이 바로잡은 전제 셋

설계 전에 믿고 있던 것들이 틀렸다. 재 보고 나서야 알았다.

### 1. 자식은 Node 프로세스가 아니다

- **`claude` 는 265MB 짜리 네이티브 exe** 다. 관측된 RSS 110 / 215 / 699MB
- **`codex` 는 네이티브 Rust 바이너리인데 앞에 낭비적인 Node shim 이 붙어 있다.** shim 을 지나 실제 바이너리를 직접 해소하면 **세션당 약 50MB 를 아낀다**

**runtrol 이 통제할 수 없는 비용과 통제할 수 있는 비용이 갈린다.** 자식의 RSS 는 우리 것이 아니지만, **shim 을 우회하는 것과 몇 개를 살려두느냐는 우리 것이다.**

### 2. CLI 에 물어보는 것이 파일을 읽는 것보다 9,000 배 느리다

**`claude agents --json` 이 39.9 초 걸린다. 같은 데이터를 파일 세 개에서 읽으면 4.4 밀리초다.**

프로세스 spawn 자체도 이 기계에서 약 300ms 바닥이 있다.

이것이 세션 목록 설계를 결정한다. **목록은 CLI 를 불러서 만들지 않는다. provider 자신의 저장소를 읽어서 만든다.** 얇음 원칙 ([[thinPrinciple]]) 과 성능이 같은 답을 가리킨다.

### 3. transcript 는 검증 가능하게 append-only 다

이 기계의 transcript 총량: **2,416 파일에 1,904MB**, 최대 파일 144.7MB.

**앞부분 해시가 파일이 자라는 동안 변하지 않는다.** 즉 append-only 이고, 따라서 **바이트 오프셋이 내구성 있는 커서**다.

**2026-07-30 통제 실험으로 재확인** (`tests/_attempts/providerProbe/probeClaudeResume.py`). 세션 하나를 `--resume` 으로 이어 돌리고 전후를 쟀다.

| | 재개 전 | 재개 후 |
|---|---:|---:|
| 크기 | 17,877 B | 22,339 B (+4,462) |
| 줄 | 11 | 19 (+8) |
| 앞 4,096B 해시 | `8f68f9a36e7e365f` | `8f68f9a36e7e365f` **동일** |

같은 파일, 앞부분 불변, 뒤로만 자람. 관측이 아니라 **통제 실험으로 확인된 성질**이다.

**이것이 "runtrol 은 사본을 갖지 않는다" 를 기술적으로 가능하게 만드는 사실이다.** 커서만 들고 있으면 언제든 그 지점부터 읽을 수 있다.

## 버퍼링 입장 . 사본 0

**64KiB 재생 링은 지연 창(latency window) 이지 히스토리가 아니다.** 그보다 오래된 것은 provider 파일에 대한 **위치 지정 읽기**로 처리한다.

측정된 차이:

| 방식 | 시간 | 메모리 |
|---|---:|---:|
| 위치 지정 읽기 64KiB | **1.1 ms** | 64KiB |
| 전체 실체화 | 173 ms | **145 MB** |

**spill-to-disk 도 하지 않는다.** 디스크에 흘릴 사본이 애초에 없다. provider 의 파일이 이미 그 역할을 한다.

## 확정 숫자 (게이트가 이 값을 강제한다)

바닥 실측: **private working set 1.43MB**.

| 상태 | 상한 |
|---|---:|
| 유휴 | **6 MB** |
| 세션 1,000 개 색인됨 | **9 MB** |
| hot 8 개 + 구독자 4 개 | **18 MB** |
| **하드 천장** | **48 MB** |

단위당 비용:

| 단위 | 비용 |
|---|---:|
| cold 행 | **256 B** |
| warm 리더 | **8 KiB** |
| hot 세션 | **128 KiB** |
| 구독자 | **20 KiB** |

**상한은 내려가기만 하는 ratchet 이다.** 올리려면 운영자 승인.

## backpressure . 위치를 버리되 데이터를 버리지 않는다

프레임은 조밀한 `seq` + `src_end` 를 갖는다. 큐는 **64 프레임 / 256KiB 로 유한**하다.

넘치면 **데몬은 그 구독자의 위치를 버린다. 데이터는 절대 버리지 않는다.** 클라이언트는 provider 파일에서 범위 복구한다.

이것이 느린 모바일 링크가 데몬을 OOM 시킬 수 없는 이유이고, 동시에 출력 손실이 0 인 이유다. **버릴 것이 위치뿐이라 안전하다** (데이터의 정본이 우리 것이 아니기 때문에 가능한 설계다).

fan-out 은 zero-parse `Bytes` 다.

## 런타임 세부

- tokio **`current_thread`**, `max_blocking_threads(8)`
- 실측: `current_thread` 는 순수 std 대비 **+0.02MB, 스레드 0 개**. `multi_thread` 는 **+0.5MB, 스레드 16 개** (이 16 코어 기계에서)
- 직접 의존 **17 개**, MSRV 1.89
- **`panic = "abort"` 를 거부한다. `unwind` 를 쓴다.** 감독자는 태스크 하나의 패닉에서 살아남아야 한다. 세션 하나가 죽었다고 데몬 전체가 죽으면 감독자가 아니다
  (주의: [01-runtime-measurements.md](01-runtime-measurements.md) 의 비교 벤치는 `panic="abort"` 프로파일로 쟀다. 그건 **측정 조건**이지 제품 프로파일이 아니다. 제품은 `unwind` 이므로 실제 바이너리는 그 표보다 약간 크다)
- 커스텀 할당자 없음

## `pwaConnection` 과의 충돌 . 양보했고, 조건 셋을 남긴다

이 설계는 원래 SSE 를 골랐고, [pwaConnection](../pwaConnection/README.md) 은 프레임 바이너리 스트림을 골랐다. **프레임 스트림으로 양보한다** (전송 전환·재개 오프셋·다중 클라이언트에서 그쪽이 옳다).

넘어가면서 반드시 지켜야 할 것:

1. **tungstenite 의 `max_write_buffer_size` 기본값이 무제한이다.** 그대로 두면 **메모리 계약이 조용히 무너진다.** 명시적으로 묶고 게이트로 잠근다
2. 조밀한 `seq` + `src_end` 는 프레임에도 그대로 실린다 (범위 복구의 전제)
3. overflow 시 위치를 버리는 정책은 전송 계층이 바뀌어도 유지된다

## 게이트

- `idleFootprintRatchet`: 위 표의 네 상태를 실측하고 상한 초과 시 red
- `redbCacheBounded`: redb 캐시가 기본 1 GiB 로 열리는 코드 경로가 없다
- `wsWriteBufferBounded`: 웹소켓 쓰기 버퍼 상한이 명시돼 있다
- `noTranscriptCopy`: provider 세션 파일을 통째로 메모리에 올리는 코드가 없다
- `panicIsolation`: 세션 태스크 패닉이 데몬을 죽이지 않는다
