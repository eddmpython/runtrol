# 저장소 결정 . redb

## 결정

**redb 4.1.0 이상을 직접 쓴다.** `Builder::set_cache_size` 로 기본값 1 GiB 를 낮춘다.

이 결정은 처리량이 아니라 **북극성 두 축**이 골랐다: `상주 비용` (배터리·팬·작업 관리자에서 안 보인다) 과 `어디서나 같은 방법` (Windows 사용자가 아무것도 더 안 깐다).

## 왜 redb 인가

### 1. 유휴 RSS 가 측정됐고 작다

redb 자신의 최적화 PR 두 건이 최근에 이 숫자를 크게 바꿨다. **석 달 된 사실이다.**

[PR #1111](https://github.com/cberner/redb/pull/1111) (3.1.2, 2026-04-01). 원인: `RegionTracker::new()` 가 빈 DB 에도 비트맵 21 개 x 128KB 를 잡았다.

| 판본 | 질의 후 RSS | DB 오버헤드 |
|---|---:|---:|
| redb v3 (원본) | 9,488 KB | 약 7,268 KB |
| redb v3 (PR, 파일 백엔드) | **2,872 KB** | **약 760 KB** |

[PR #1137](https://github.com/cberner/redb/pull/1137) (4.1.0, 2026-04-19). 원인: region 마다 `BuddyAllocator` 가 아직 존재하지 않는 페이지까지 비트맵으로 미리 잡았다 (region 당 약 256KB).

| 지표 | 이전 | 이후 | 변화 |
|---|---:|---:|---:|
| DB **32 개** 연 뒤 VmRSS | 12,892 KB | **4,112 KB** | -68% |
| 최대 RSS | 12,812 KB | **3,960 KB** | -69% |
| 피크 live heap (DHAT) | 9.92 MB | **1.17 MB** | -88% |

**작은 redb 는 프로세스 RSS 약 1~4MB 다.** 3.1.1 이하에서는 DB 하나에 약 9.5MB 였다. **4.1.0 미만을 핀하지 않는다.**

### 2. 필수 의존성 0. C 컴파일러 불필요

`log`·`chrono`·`uuid` 전부 optional feature 다. 순수 Rust.

**heed/LMDB 와 libmdbx 는 Windows 에서 MSVC Build Tools 를 요구한다.** `mdb.c` 를 `cc` 로 빌드하기 때문이다. 북극성에 "Windows 사용자가 WSL 이나 tmux 를 알 필요가 없다" 를 적어놓고 빌드 도구 설치를 요구하는 것은 모순이다.

### 3. 배경 스레드가 없다

**이것이 결정타다.** compaction 은 `compact()` 를 직접 부를 때만 돈다.

fjall 은 배경 flush·compaction 스레드를 상시 돌린다. **하루 23 시간 유휴인 기계에서 그건 완전히 억제할 수 없는 팬과 배터리다.** `상주 비용` 축이 정확히 그것을 금지한다.

### 4. 상태가 정직하다

README 가 "Stable and maintained. The file format is stable" 이라고 명시한다. 월 약 1.5 회 릴리즈. 4.1.0/4.2.0 체인지로그가 데이터 손실 버그 수정으로 빽빽하다 (유지보수자가 능동적으로 정합성 버그를 사냥하고 있다는 신호다).

### 5. 워크로드가 B-tree 모양이다

runtrol 이 저장하는 것: 세션·어댑터 행 수백~수천 개 + 단조 증가 키의 append-only 이벤트 로그. 단조 u64 키는 오른쪽 가장자리에 싸게 붙는다.

**durability 를 갈라 쓴다** (sled 에서 이주한 qsv 가 쓴 방식과 같다):

- 고빈도 이벤트 로그: `Durability::None` 또는 `Eventual`
- 세션 메타데이터: `Immediate`

로그 절단은 `Table::retain()` / `extract_if()`. 미출시 4.2.0 에서 각각 30~100 배, 18~65 배 빨라진다.

## 주의할 것

**redb 는 이 그룹에서 공간 증폭이 가장 나쁘다** (100 만 행 벤치에서 미압축 4.00 GiB, LMDB 는 2.61 GiB).

append-only 로그를 두는 이상 **보존 기간을 반드시 묶고 `compact()` 를 주기적으로 부른다.** 안 그러면 파일이 자란다. 이것을 게이트로 잠근다 (`storageGrowthRatchet`).

4.0.0 이 `Legacy` 타입을 제거했다. 핀 버전을 확인한다.

## 기각한 것들

### sled . 절대 안 쓴다

| 근거 | 내용 |
|---|---|
| 동결 | 마지막 stable 이 **0.34.7 (2021)**. `1.0.0-alpha.124` (2024-10-11) 에서 21 개월 정지. 최근 14 개월간 커밋한 날이 약 5 일 |
| 메모리 | **#986 (2020, 아직 열림)**: 작은 값 21 만 개에 "메모리가 폭발해서 5GB 를 찍고 이후 3GB 아래로 안 내려간다". **#1410 (아직 열림)**: `cache_capacity = 1 MiB` 인데 **1GB DB 를 여는 것만으로 RSS 500MB**. 질의 전에, 여는 시점에 219MB 를 할당한다 |
| 제3자 확인 | fjall 2.0 벤치: "sled 가 약 **11GB** 를 먹어서 **실격**" |
| 내구성 | fjall 3.0 벤치가 세 절에서 반복: "**sled 는 신뢰성 있게 fsync 하지 않아서 포함하지 않는다**" |
| 퇴출 | **redb 저장소에서 sled 가 통째로 제거됐다.** 전체 코드 검색 결과 0 건 |
| 공급망 | 전이 의존 `fxhash` 에 unmaintained 권고 |
| 저자 본인 README | "신뢰성이 최우선이면 **SQLite 를 써라. sled 는 beta 다**", "sled 는 **가끔 공간을 너무 많이 쓴다**", "on-disk 포맷이 1.0 전에 **수동 마이그레이션이 필요한 방식으로 바뀔 것**" |

**생태계가 실제로 떠났다**: `cached` 크레이트가 2026-07-13 에 sled 를 redb 로 교체했고 ("redb 는 적극 유지보수되고, 현재 stable Rust 에서 깨끗이 컴파일되며, ACID 트랜잭션이 blob 누수 버그를 없앤다"), 그 하류 qsv 도 따라갔다. freedit, hstdb, guardian-db, comrade, rpc-utreexo-bridge, wikipath 전부 같은 이주를 했다.

### fjall . 2 순위로 남긴다

건강하다 (3.1.8, 2026-07-18, 릴리즈 활발, MSRV 1.90, `forbid(unsafe)`, mmap 안 씀, hello-world 바이너리 약 2.2MB / 컴파일 약 3.5 초). **쓰기 증폭과 삭제 처리량은 redb 보다 낫다.**

그런데 두 가지가 runtrol 의 모양과 정면으로 안 맞는다.

- **배경 스레드 상시 가동** (위 3 번)
- **[#288](https://github.com/fjall-rs/fjall/issues/288) (열림)**: 유휴 keyspace 의 sealed journal 이 flush 되지 못해 **저널이 무한히 자라고 시작이 느려진다.** 보고자 표현: "저널 크기가 무한히 자라서 애플리케이션이 부풀어 시작 프로브 타임아웃 안에 못 끝난다". **대부분 유휴인 데스크톱 데몬이 정확히 이 모양이다**
- [#276](https://github.com/fjall-rs/fjall/issues/276) (열림, **Windows 에서 보고됨**): KV 분리 + 100 만 키에서 콜드 스타트 메모리 스파이크

**이벤트 로그가 메타데이터 수준이 아니라 초당 수천 건의 스트리밍이 되면** 그때 fjall 을 다시 본다.

### heed / LMDB . 3 순위

**정지 상태에서 가장 가볍고 크래시 안전성 이야기가 가장 강하다** (copy-on-write, 크래시 후 특별 복구 절차 불필요, WAL 없음, 유지보수 불필요, 배경 스레드 없음). 지금도 매력적이다.

기각 사유:

- **Windows 에서 MSVC Build Tools 필요** (위 2 번)
- **`map_size` 를 미리 정해야 한다.** 안 정하면 기본값이 **1 MiB** 다 (`mdb.c` 소스 기준. `lmdb.h` 주석은 10MB 라고 하는데 코드와 다르다). 넘치면 `MDB_MAP_FULL`, 늘리려면 활성 트랜잭션이 없어야 하는데 **라이브러리가 그 조건을 검사하지 않는다**
- **Windows 최대 64 environment**, macOS 쓰기 트랜잭션 10 개 제한. heed 문서가 아직 이걸 노출 안 한다 (heed#150, 2023 년부터 열림)
- **mmap 회계가 관측을 혼란스럽게 한다.** 매핑된 파일 페이지는 공유 working set 에 들어가 **작업 관리자 프로세스 탭의 메모리 열에는 거의 안 보인다.** 숫자가 좋아 보이지만 도구마다 전혀 다른 값을 보고하고, 예약된 주소공간이 커밋 크기로 잡혀 `map_size` 를 크게 잡으면 놀랍게 보인다. **정직한 계측을 원하는 프로젝트에 맞지 않는다**
- zero-copy + mmap 조합의 함정: 트랜잭션 밖으로 참조를 들고 있으면 페이지가 상주로 고정된다 (heed#337 실사례)
- `MDB_MAXKEYSIZE` 511 바이트. 세션 ID 는 되지만 임의 경로를 키로 못 쓴다

`map_size` 추측이 싫으면 **libmdbx 0.6.6** 이 자동 geometry 성장을 준다. 다만 C 컴파일러 요구는 동일하다.

### canopydb . 설계는 좋은데 못 쓴다

개별 쓰기가 이 그룹에서 가장 빠르다 (404ms). 그런데 **README 가 직접 "초기 단계 소프트웨어로 봐야 하고 프로덕션 데이터를 맡기지 말라" 고 적었다.** star 160, 총 다운로드 6,353, **8 개월간 커밋 0.**

### native_db . 값어치가 없다

redb 위의 스키마 레이어. **마지막 릴리즈 2025-07-08 (12 개월 이상)**, 최근 커밋은 전부 Renovate 의존성 범프.

치명적: **`redb = "=3.0.2"` 를 `=` 로 핀했다.** redb 는 4.1.0 이다. 즉 **위에서 실측한 -68% 메모리 개선을 못 받는다.** 대가로 얻는 마이그레이션 도우미는 직접 쓰면 30 줄이다.

행 수백~수천 개짜리 인덱스에 proc-macro 층 + serde/bincode 왕복 (zero-copy 없음) + 보조 키마다 redb 테이블 하나를 더 얹을 이유가 없다. **redb 를 직접 쓰고 값 앞에 스키마 버전 바이트를 붙인다.**

## 게이트로 옮길 것

- `idleFootprintRatchet` 의 저장소 몫 상한: 빈 DB 기준 약 4MB 이하
- `storageGrowthRatchet`: 이벤트 로그 보존 정책이 지켜지고 `compact()` 후 파일이 예상 범위 안
- `noBackgroundThreads`: 유휴 상태에서 저장소가 스레드를 돌리지 않음
- 의존성 검사: 저장소 계층이 C 툴체인을 요구하지 않음 (Windows 설치 동등성)
