# desktopGui

상태: 활성. `coreRuntime` 과 `providerAdapter` 위에 선다. **셸은 Tauri v2 로 확정됐다** (실측, 아래).

## 한 문장 정의

**PC 앞에서 여러 AI 세션을 다루는 로컬 GUI.** 운영자 지시: **"GPT 앱을 참고한다. GPT 앱이 진짜 관리하는 건 편하다. 세션 관리가 메모리가 많아지면 빡쳐서 그렇지 편하긴 하다. 잘 만든 앱이다."**

그래서 목표가 정확히 이렇게 정해진다.

> **GPT 앱의 편의를 가져오되, 그 메모리는 가져오지 않는다.**

## GPT 앱에서 가져올 것 (편의)

운영자가 "편하다" 고 지목한 것들을 동작 단위로 분해한다. 이것이 GUI 요구사항 정본이다.

| 가져올 동작 | 왜 편한가 | runtrol 에서의 형태 |
|---|---|---|
| **세션 목록이 항상 왼쪽에 있다** | 어디에 있는지 찾을 필요가 없다. 위치가 고정이라 근육 기억이 생긴다 | provider 를 가로질러 하나의 목록. provider 는 행의 뱃지이지 탭이 아니다 |
| **누르면 즉시 열린다** | 기다림을 인지하는 순간이 없다 | 가상 스크롤 + 꼬리부터 점진 로딩. transcript 전체를 안 읽는다 |
| **새 대화 버튼이 늘 같은 자리** | 시작 비용이 0 에 가깝다 | 새 세션은 **provider 선택 없이** 시작 가능해야 한다 (마지막에 쓴 것이 기본값) |
| **검색으로 옛 대화를 찾는다** | 목록이 길어져도 안 무섭다 | **얇음 주의**: 본문 색인을 우리가 만들지 않는다. provider 파일에 대한 on-demand 검색 |
| **제목이 알아서 붙는다** | 이름 짓는 일을 안 시킨다 | provider 가 제목을 주면 쓰고, 없으면 첫 지시 앞부분. **우리가 요약 모델을 돌리지 않는다** |
| **스트리밍이 자연스럽다** | 지금 살아있다는 감각 | 프레임 스트림 그대로 렌더. 재조립 안 함 |

**GPT 앱에 없는 것도 하나 더한다: 사용량과 한도가 보인다.** rate limit 대기는 이 카테고리 사용자의 일상 스트레스인데 (첫 probe 에서 71.8 초 대기 실측) 두 CLI 모두 그것을 구조화해 내준다 (`rate_limit_event` · `account/rateLimits/read`). 숨겨진 대기를 보이게 만드는 것이 편의다. "왜 안 되지" 가 "한도 리셋까지 12 분" 으로 바뀐다.

구현 상태 (2026-08-01): 새 세션 창은 성공적으로 시작한 마지막 공급자를 로컬 기본값으로 기억하며, 공급자를 다시 고르지 않아도 시작할 수 있다. `UsageUpdate` 와 `RateLimitUpdate` 는 대화 행으로 섞지 않고 헤더의 문맥 사용량과 단기 및 장기 한도로 표시한다. 한도 도달과 공급자가 준 재설정 시각도 그대로 보인다. production bundle 의 이 동작은 `desktopConvenienceSmoke` 가 실물 브라우저에서 누르고 확인한다.

## GPT 앱에서 안 가져올 것

- **메모리 증가.** 운영자가 지목한 유일한 불만이다. 대화가 쌓일수록 무거워지는 것은 **전체를 메모리에 들기 때문**이고, runtrol 은 애초에 사본을 안 갖는다 ([../coreRuntime/04-memory-contract.md](../coreRuntime/04-memory-contract.md)). 이 축이 우리가 이길 자리다
- **대화 재해석.** GPT 앱은 자기 대화의 주인이라 마음대로 렌더링한다. runtrol 은 아니다 ([[thinPrinciple]])
- **계정·로그인·동기화.** 우리는 로컬이다

## 성능 계약 (`즉시 반응` 축)

**버벅임은 최적화 대상이 아니라 버그다.**

### 이 축이 성립한다는 것이 실측으로 확인됐다 (2026-07-30)

가장 큰 위험은 GUI 가 아니라 **provider 였다.** `claude -p` 단발 호출은 시작 오버헤드만 **12.5 초**를 문다. 이게 메시지마다면 제품이 성립하지 않는다.

`--input-format stream-json` 으로 프로세스를 살려 두고 턴 3 개를 넣어 봤다.

| 턴 | 첫 이벤트 | 모델 시간 | **runtrol 이 지는 오버헤드** |
|---:|---:|---:|---:|
| 1 | 7.00 s | 3,845 ms | 6.60 s |
| 2 | **0.07 s** | 2,090 ms | **0.02 s** |
| 3 | **0.02 s** | 1,329 ms | **0.01 s** |

**시작 비용은 세션당 한 번이고, 2 번째 턴부터는 모델 시간만 남는다.** hot 세션 계층이 실측으로 검증됐다.

즉 **지연의 주인은 이제 GUI 다.** provider 핑계를 댈 수 없다.

파생 규칙 둘:

- **단발 `-p` 호출을 반복하는 설계는 금지다.** 12.5 초를 매번 문다
- **첫 턴의 6~12 초는 사용자에게 정직하게 보인다.** 새 세션을 열면 준비 중임을 표시한다. 숨기지 않는다. (rate limit 대기가 겹치면 더 길어질 수 있고, `rate_limit_event` 가 오므로 그것도 그대로 보여준다)

### cold 세션도 즉시 열린다 (지연을 없애는 게 아니라 숨긴다)

hot 상한 (8 개) 을 넘는 세션을 열면 첫 턴에 6~12 초가 붙는다. 그 순간의 경험을 설계로 못박는다: **세션을 여는 동작과 프로세스를 깨우는 동작을 분리한다.**

1. 클릭 즉시 **transcript 를 파일에서 그린다** (위치 지정 읽기 64KiB = 1.1 ms 실측). 화면에 로딩이 없다
2. 같은 순간 백그라운드에서 프로세스를 미리 깨운다 (첫 턴 오버헤드 6.6 초 실측)
3. 사용자가 옛 대화를 읽는 몇 초 동안 준비가 끝난다. 입력할 때는 대부분 이미 hot 이다
4. 아직 준비 중인데 입력하면 그 사실을 정직하게 보여준다. 숨기지 않는다

**transcript 표시는 프로세스와 무관하게 항상 즉시다.** 이것이 "대화 가져오는 거랑 버벅임도 없어야" 의 구조적 답이다.

### 상주하는 것은 데몬이다

GUI 창은 열고 닫는 앱이고, **닫아도 세션은 산다** (데몬이 본체다). 메모리 계약의 유휴 6MB / 천장 48MB 는 데몬 몫이고, GUI 창이 열렸을 때의 웹뷰 비용은 별도 예산으로 병기한다 (`idleFootprintRatchet` 이 둘을 분리 측정한다). GPT 앱의 "메모리 많아지면 빡치는" 문제는 창을 닫으면 0 이 되는 구조로 답한다.

### 상한

| 동작 | p95 상한 |
|---|---|
| 앱 실행 -> 세션 목록 첫 페인트 | 결정 필요. 목표는 사람이 로딩을 인지하지 못하는 범위 |
| 세션 클릭 -> 첫 내용 표시 | 위와 같음 |
| **이미 hot 인 세션에 입력 -> 첫 이벤트** | **provider 실측 0.02~0.07 초. GUI 가 여기에 얼마를 더하는지가 우리 몫이다** |
| 초당 수천 줄이 쏟아지는 동안 스크롤·입력 | 프레임 예산 안 |

게이트: `interactionLatencyBudget` (bench, 내려가기만 하는 ratchet) + `scrollUnderLoadSmoke`.

**나머지 숫자를 지금 확정하지 않는다.** 실물 렌더러를 세우고 실측한 뒤 그 값에서 ratchet 을 시작한다. 근거 없는 숫자를 계약이라 부르지 않는다.

## 비동기 파이프라인

운영자 지시: "정말 속도와 비동기성도 혁신적인 파이프라인으로 진행해야 해."

바닥은 이미 깔려 있다 ([../coreRuntime/](README.md)):

- 이벤트 로그 + u64 오프셋 -> **GUI 도 PWA 와 같은 커서를 쓴다.** 같은 세션을 PC 와 폰이 동시에 봐도 위치가 각자다
- backpressure 는 위치를 버리되 데이터를 안 버린다 -> GUI 가 느려도 데이터가 안 사라진다
- 위치 지정 읽기 64KiB 가 1.1ms -> **스크롤백은 메모리가 아니라 파일에서 온다**

GUI 가 추가로 지켜야 할 것:

- **렌더는 절대 I/O 를 기다리지 않는다.** 스켈레톤이 아니라 이미 가진 꼬리를 먼저 그린다
- **한 세션의 폭주가 다른 세션을 막지 않는다.** 세션당 독립 채널
- **입력은 어떤 경우에도 블록되지 않는다.** 출력 렌더와 입력 처리가 같은 큐를 공유하지 않는다

## 컴포넌트 층 . Astryx (확정)

**정본은 [docs/frontendStack.md](../../docs/frontendStack.md) 다.**

`@astryxdesign/core` (MIT, React 컴포넌트 103 개) 가 우리 화면 대부분을 이미 갖고 있다: `AppShell` + `SideNav` (좌측 세션 목록), `Chat` + `Markdown` + `CodeBlock` (대화), `CommandPalette` (빠른 전환), `StatusDot` (세션 상태), `AlertDialog` + `Toast` (승인). **새로 디자인할 것이 거의 없다.**

**단 `Skeleton` 은 남용하지 않는다.** 위 성능 계약이 "스켈레톤이 아니라 이미 가진 꼬리를 먼저 그린다" 이다. **로딩을 예쁘게 보여주는 것은 편의가 아니다. 로딩이 없는 것이 편의다.**

## GUI 셸 . Tauri v2 (확정, 2026-07-31)

**프로토타입 실측으로 정했다** (`tests/_attempts/desktopShell/`). 판정 규칙은 숫자를 보기 전에 적어 두었고 그 규칙이 답을 냈다.

| 기준 | 결과 |
|---|---|
| (1) 한글 IME · 선택 · 복사 | **둘 다 통과** (각 3/3, 기계 검증) |
| (2) 초당 3,000 줄 프레임 | **Tauri 압승** (p95 14 ms 대 106 ms) |
| (3) 메모리 | egui 유리 (private 162 대 202 MB) |
| (4) 컴포넌트 층 공유 | **Tauri** (Astryx 를 랜딩·PWA 와 공유) |
| (5) 어디서나 같은 방법 | 둘 다 3 OS. 무승부 |

**(1) 이 갈리지 않았으므로 (2) 가 결정하고 (4) 가 같은 방향으로 얹힌다.** 메모리 40 MB 차이는 그 둘을 뒤집지 못한다 (GUI 창 비용은 데몬 예산과 분리해 병기하기로 이미 정해져 있고, 창을 닫으면 0 이 된다).

**두 가지를 기록해 둔다.** 첫째, 사전 가설은 "egui 가 한글에서 걸린다" 였고 **틀렸다.** egui 는 조합을 정확히 받는다. 통념으로 후보를 떨어뜨릴 뻔했다. 둘째, egui probe 는 튜닝하지 않은 구현이라 (2) 의 숫자에 개선 여지가 있다. 그래도 5 배 가까운 격차와 (4) 를 뒤집지는 못한다.

**한글 IME 는 사람이 매번 확인할 일이 아니다.** 가상 키를 보내면 IME 가 평소대로 동작하고, 앱이 받은 조합 이벤트를 되읽으면 기계가 판정할 수 있다 (`tests/_attempts/desktopShell/imeDrive.ps1`). 완료 판정의 "한글 입력·텍스트 선택·복사가 실물로 확인된다" 는 이 방식으로 게이트가 된다.

### 후보 표 (판정 당시)

**판정 기준 (이 순서로)**: (1) 한글 IME 와 텍스트 선택이 제대로 되는가 (2) 초당 수천 줄에서 프레임 예산을 지키는가 (3) 유휴 RSS 가 메모리 계약 안인가 (4) 컴포넌트 층을 얼마나 공유하는가 (5) Windows·macOS·Linux 가 같은 방법인가.

**(1) 을 첫 기준으로 둔 이유**: 한글 입력이 안 되는 GUI 는 나머지가 아무리 빨라도 운영자가 못 쓴다. 사용자 편의가 최상위 원칙이고, 컴포넌트 공유라는 강한 이점도 그 바닥 조건을 이기지 못한다. 실제로는 (1) 에서 갈리지 않았고, 그래서 (2) 가 결정했다.

### (2) 와 (3) 실측 완료 (2026-07-31, `tests/_attempts/desktopShell/`)

두 후보에 같은 화면을 짓고 쟀다: 2,000 줄 유계 스크롤백, 초당 3,000 줄 쏟아붓기, 한글 섞인 줄, release 빌드, 예산선 60Hz.

| | egui | Tauri (WebView2) |
|---|---|---|
| 첫 페인트 | 1,553 ~ 1,968 ms | **1,015 ~ 1,264 ms** |
| 쏟아붓기 p95 | 17.1 ~ 105.7 ms | **7.2 ~ 14.1 ms** |
| 쏟아붓기 최대 | 207.5 ms | **14 ms 대** |
| 예산 초과 프레임 | 대부분의 초에서 과반 | **초당 0 ~ 1** |
| 유휴 working set | **167.8 MB** (1 프로세스) | 423.8 MB (7 프로세스) |
| 유휴 private | **161.6 MB** | 202.1 MB |

**(2) 는 Tauri 압승이고 통념과 반대다.** 웹뷰가 느릴 것이라는 예상이 틀렸다. 첫 페인트도 Tauri 가 빠르다.

**(3) 은 지표를 고르는 순간 결론이 뒤집힌다.** working set 은 공유 페이지를 매핑한 프로세스마다 중복으로 세므로 런타임을 7 개 프로세스가 나눠 쓰는 WebView2 에 크게 불리하다. 이 앱만의 몫인 private 로 보면 격차가 202 대 162 MB 로 좁혀진다. **한 지표만 적으면 지표 선택이 판정을 대신하므로 둘 다 적는다.**

단서 셋 (이 기계 화면이 고주사율이라 프레임 개수의 뜻이 서로 다르다 · egui probe 는 튜닝하지 않은 평범한 구현이다 · Tauri probe 의 rAF 는 유휴에도 돌아서 유휴 CPU 는 이 표에 없다) 은 캠페인 원장에 적혀 있다.

### (1) 도 기계가 쟀다

처음에는 자동화 불가로 적었고 **틀렸다.** 유니코드 문자를 주입하면 IME 를 건너뛰는 것은 맞지만, **가상 키**를 보내면 키보드와 앱 사이의 IME 가 평소 하던 일을 그대로 한다. 2 벌식 물리 키를 보내고 앱이 받은 조합 이벤트를 되읽으면, 서로 독립인 두 곳 (조합 경로가 살아 있다 · 거기서 옳은 글자가 나왔다) 이 일치해야 통과가 된다. 선택·복사는 Ctrl+A / Ctrl+C 뒤 클립보드를 되읽어 확인한다.

각 후보 3 회씩 전부 통과했다. 하네스가 스스로 만든 거짓 음성 셋 (콘솔 창이 포그라운드를 가로챔 · 스레드 부착 대상 오류 · 한/영 토글이 판마다 다르게 먹음) 은 캠페인 원장에 기록했고, 드라이버는 **포커스를 못 잡으면 판정 대신 중단한다.** 거짓 음성은 답이 없는 것보다 나쁘다.
