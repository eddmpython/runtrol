# desktopGui

상태: 활성 설계. `coreRuntime` 과 `providerAdapter` 위에 선다.

## 한 문장 정의

**PC 앞에서 여러 AI 세션을 다루는 로컬 GUI.** 운영자 지시: **"GPT 앱을 참고한다. GPT 앱이 진짜 관리하는 건 편하다. 세션 관리가 메모리가 많아지면 빡쳐서 그렇지 편하긴 하다. 잘 만든 앱이다."**

그래서 목표가 정확히 이렇게 정해진다.

> **GPT 앱의 편의를 가져오되, 그 메모리는 가져오지 않는다.**

## GPT 앱에서 가져올 것 (편의)

운영자가 "편하다" 고 지목한 것들을 동작 단위로 분해한다. 이것이 GUI 요구사항 정본이다.

| 가져올 동작 | 왜 편한가 | runtrol 에서의 형태 |
|---|---|---|
| **세션 목록이 항상 왼쪽에 있다** | 어디에 있는지 찾을 필요가 없다. 위치가 고정이라 근육 기억이 생긴다 | provider 를 가로질러 하나의 목록. provider 는 행의 뱃지이지 탭이 아니다 |
| **누르면 즉시 열린다** | 기다림을 인지하는 순간이 없다 | 가상 스크롤 + 꼬리부터 점진 로딩. transcript 전체를 안 읽는다 |
| **새 대화 버튼이 늘 같은 자리** | 시작 비용이 0 에 가깝다 | 새 세션은 **provider 선택 없이** 시작 가능해야 한다 (마지막에 쓴 것이 기본값) |
| **검색으로 옛 대화를 찾는다** | 목록이 길어져도 안 무섭다 | **얇음 주의**: 본문 색인을 우리가 만들지 않는다. provider 파일에 대한 on-demand 검색 |
| **제목이 알아서 붙는다** | 이름 짓는 일을 안 시킨다 | provider 가 제목을 주면 쓰고, 없으면 첫 지시 앞부분. **우리가 요약 모델을 돌리지 않는다** |
| **스트리밍이 자연스럽다** | 지금 살아있다는 감각 | 프레임 스트림 그대로 렌더. 재조립 안 함 |

## GPT 앱에서 안 가져올 것

- **메모리 증가.** 운영자가 지목한 유일한 불만이다. 대화가 쌓일수록 무거워지는 것은 **전체를 메모리에 들기 때문**이고, runtrol 은 애초에 사본을 안 갖는다 ([../coreRuntime/04-memory-contract.md](../coreRuntime/04-memory-contract.md)). 이 축이 우리가 이길 자리다
- **대화 재해석.** GPT 앱은 자기 대화의 주인이라 마음대로 렌더링한다. runtrol 은 아니다 ([[thinPrinciple]])
- **계정·로그인·동기화.** 우리는 로컬이다

## 성능 계약 (`즉시 반응` 축)

**버벅임은 최적화 대상이 아니라 버그다.**

### 이 축이 성립한다는 것이 실측으로 확인됐다 (2026-07-30)

가장 큰 위험은 GUI 가 아니라 **provider 였다.** `claude -p` 단발 호출은 시작 오버헤드만 **12.5 초**를 문다. 이게 메시지마다면 제품이 성립하지 않는다.

`--input-format stream-json` 으로 프로세스를 살려 두고 턴 3 개를 넣어 봤다.

| 턴 | 첫 이벤트 | 모델 시간 | **runtrol 이 지는 오버헤드** |
|---:|---:|---:|---:|
| 1 | 7.00 s | 3,845 ms | 6.60 s |
| 2 | **0.07 s** | 2,090 ms | **0.02 s** |
| 3 | **0.02 s** | 1,329 ms | **0.01 s** |

**시작 비용은 세션당 한 번이고, 2 번째 턴부터는 모델 시간만 남는다.** hot 세션 계층이 실측으로 검증됐다.

즉 **지연의 주인은 이제 GUI 다.** provider 핑계를 댈 수 없다.

파생 규칙 둘:

- **단발 `-p` 호출을 반복하는 설계는 금지다.** 12.5 초를 매번 문다
- **첫 턴의 6~12 초는 사용자에게 정직하게 보인다.** 새 세션을 열면 준비 중임을 표시한다. 숨기지 않는다. (rate limit 대기가 겹치면 더 길어질 수 있고, `rate_limit_event` 가 오므로 그것도 그대로 보여준다)

### 상한

| 동작 | p95 상한 |
|---|---|
| 앱 실행 -> 세션 목록 첫 페인트 | 결정 필요. 목표는 사람이 로딩을 인지하지 못하는 범위 |
| 세션 클릭 -> 첫 내용 표시 | 위와 같음 |
| **이미 hot 인 세션에 입력 -> 첫 이벤트** | **provider 실측 0.02~0.07 초. GUI 가 여기에 얼마를 더하는지가 우리 몫이다** |
| 초당 수천 줄이 쏟아지는 동안 스크롤·입력 | 프레임 예산 안 |

게이트: `interactionLatencyBudget` (bench, 내려가기만 하는 ratchet) + `scrollUnderLoadSmoke`.

**나머지 숫자를 지금 확정하지 않는다.** 실물 렌더러를 세우고 실측한 뒤 그 값에서 ratchet 을 시작한다. 근거 없는 숫자를 계약이라 부르지 않는다.

## 비동기 파이프라인

운영자 지시: "정말 속도와 비동기성도 혁신적인 파이프라인으로 진행해야 해."

바닥은 이미 깔려 있다 ([../coreRuntime/](README.md)):

- 이벤트 로그 + u64 오프셋 -> **GUI 도 PWA 와 같은 커서를 쓴다.** 같은 세션을 PC 와 폰이 동시에 봐도 위치가 각자다
- backpressure 는 위치를 버리되 데이터를 안 버린다 -> GUI 가 느려도 데이터가 안 사라진다
- 위치 지정 읽기 64KiB 가 1.1ms -> **스크롤백은 메모리가 아니라 파일에서 온다**

GUI 가 추가로 지켜야 할 것:

- **렌더는 절대 I/O 를 기다리지 않는다.** 스켈레톤이 아니라 이미 가진 꼬리를 먼저 그린다
- **한 세션의 폭주가 다른 세션을 막지 않는다.** 세션당 독립 채널
- **입력은 어떤 경우에도 블록되지 않는다.** 출력 렌더와 입력 처리가 같은 큐를 공유하지 않는다

## 컴포넌트 층 . Astryx (확정)

**정본은 [docs/frontendStack.md](../../docs/frontendStack.md) 다.**

`@astryxdesign/core` (MIT, React 컴포넌트 103 개) 가 우리 화면 대부분을 이미 갖고 있다: `AppShell` + `SideNav` (좌측 세션 목록), `Chat` + `Markdown` + `CodeBlock` (대화), `CommandPalette` (빠른 전환), `StatusDot` (세션 상태), `AlertDialog` + `Toast` (승인). **새로 디자인할 것이 거의 없다.**

**단 `Skeleton` 은 남용하지 않는다.** 위 성능 계약이 "스켈레톤이 아니라 이미 가진 꼬리를 먼저 그린다" 이다. **로딩을 예쁘게 보여주는 것은 편의가 아니다. 로딩이 없는 것이 편의다.**

## 아직 안 정한 것 . GUI 셸

후보와 판정 기준만 고정한다. 선택은 프로토타입 실측 후에 한다 (`tests/_attempts/desktopShell/`).

| 후보 | 강점 | 위험 |
|---|---|---|
| **Tauri v2** | Astryx 가 React 라 **랜딩·PWA·데스크톱이 같은 컴포넌트 층을 공유**한다. `공급자 확장성` 축의 "PC 화면과 폰 화면이 그대로" 가 규율이 아니라 구조로 보장된다. 형제 프로젝트 clipscout 의 실전 경험 (+ updater 배선) 이 있다. WebView2 는 Windows 에 이미 있다 | 웹뷰 프로세스 비용. 초기 페인트 지연 |
| **egui** | 즉시 모드, 가볍고 빠름, 순수 Rust | 텍스트 렌더·접근성·IME 가 약하다. **Astryx 를 못 쓰므로 데스크톱만 다른 컴포넌트 세계가 된다** |
| **iced / Dioxus / slint** | 각각 retained 모드, 웹 유사 DSL, 선언형 | 위와 같은 분기 위험 + 생태계·텍스트 품질 실측 필요 |

Astryx 채택이 **Tauri 쪽으로 무게를 크게 옮겼다.** 그래도 확정하지 않는 이유는 판정 기준의 순서 때문이다.

**판정 기준 (이 순서로)**: (1) 한글 IME 와 텍스트 선택이 제대로 되는가 (2) 초당 수천 줄에서 프레임 예산을 지키는가 (3) 유휴 RSS 가 메모리 계약 안인가 (4) 컴포넌트 층을 얼마나 공유하는가 (5) Windows·macOS·Linux 가 같은 방법인가.

**(1) 을 첫 기준으로 두는 이유**: 한글 입력이 안 되는 GUI 는 나머지가 아무리 빨라도 운영자가 못 쓴다. 사용자 편의가 최상위 원칙이고, 컴포넌트 공유라는 강한 이점도 그 바닥 조건을 이기지 못한다.

## 완료 판정

- `interactionLatencyBudget` 과 `scrollUnderLoadSmoke` 가 CI 에서 돈다
- 두 provider 세션이 한 목록에 뜨고 거기서 시작·재개·삭제가 끝난다
- 앱을 하루 종일 켜 둬도 메모리 계약 안에 있다 (`idleFootprintRatchet` 에 GUI 포함)
- 한글 입력·텍스트 선택·복사가 실물로 확인된다
